# 51 决赛按任务 ID 查询与发布边界

状态：`DESIGN_REVIEW`。本轮只核对和说明现有决赛授权，不向任何队伍授予 FINAL 模式，不开放任务。

## 当前事实

51 已有 `GET /v1/final/tasks/{task_id}`，以及以同一个 `{task_id}` 为路径参数的 Metadata、Topology、Metrics/Logs/Traces 和提交接口。用 `?task_id=...` 查询参数可以实现同样的导航，但现有路径参数已足够，无需新增一套接口。

`GET /v1/final/tasks` 对普通队伍只列出当前可见任务。未开放任务不会出现在列表，猜测 `FT-01` 或 `PK-R01` 的详情也返回 404。FT 需任务状态 `OPEN` 且在服务端 UTC 窗口内；PK 还要求轮次 `RUNNING` 且队伍是该轮的擂主或挑战者。提交时数据库再次核对窗口、队伍和额度。当前 17 队尚无 `FINAL` 模式权限，11 个决赛任务及 8 个 PK 轮次全为 `NOT_OPEN`。

## 推荐发布方式

可以在正式赛前给合格队伍统一增加 `FINAL` 模式权限，但继续保持所有任务 `NOT_OPEN`。开放某题时由 51 审核并绑定真实 Case、确认 GT/评分版本与时间窗，再原子切换该任务或 PK 轮次状态。此时才向参赛队公布任务 ID；选手用已有详情接口取题。若希望 Web 必须手动输入任务 ID，可把选手页面改为输入框，但这只是交互选择，不是安全边界。

任务 ID 如 `FT-01`、`PK-R01` 很容易猜到，因此**不能靠不公布 ID 来保密**。真正的隔离必须由服务器按 Token/IP、`FINAL` 模式、任务状态和 UTC 时间，以及 PK 双方身份逐次校验；未开放任务的 Case ID、时间窗和 Public 数据都不能在队伍接口提前返回。列表接口在未开放时为空；开放后的任务出现在列表属于正常发布，不构成提前泄漏。

## 验收矩阵

在独立内测身份或未开放测试任务上验证：有 FINAL 模式但任务未开时列表为空，已猜到 ID 的详情/数据/提交均拒绝；FT 开放后所有获授权队伍只见该 FT；PK 开放后仅本轮双方可见和提交；非参赛队、错误 IP、窗口外请求仍被拒绝；任务关闭后不得新增提交；历史提交按原规则可查。保持正式 GT 与评分规则只在 Private Grader，不能通过任务元数据泄漏。

因此目前不需要为“按 ID 请求”改动 51 API。是否把 52–68 的 Web 从“展示当前可见任务”改成“手工输入任务 ID”，可在确定比赛现场交题方式后单独调整，服务器权限逻辑不应因此削弱。
